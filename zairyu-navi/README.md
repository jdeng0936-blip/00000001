# 在留导航（第一期）

面向在日本生活和准备来日本的中国人：从旅游签、在留卡到永驻，每一步要办什么、什么时候办、多少钱、找谁帮忙。

第一期范围：闯关路线、提醒、选方案、助手、对接咨询。同城板块在第三期。

## 运行

需要 Node 22.5 以上，不需要安装任何依赖。

```
npm test          # 单元和接口测试
npm run e2e       # 网页端的端到端检查（需要 playwright）；发布前两个都要跑
npm start         # http://localhost:8787 ，网页在根路径，接口在 /api
npm run remind    # 期限提醒邮件跑一轮就退出（给 cron 用；也可以让 npm start 自己定时跑，见下面 REMINDERS_ENABLED）
npm run billing   # 服务商展示费和新咨询通知跑一轮就退出（给 cron 用；npm start 自己也每分钟、每小时跑，见下面“服务商入驻”）
```

环境变量：`PORT`、`DB_FILE`（SQLite 文件位置）、`ADMIN_TOKENS`（有名字的管理员令牌，写法 `名字:令牌,名字:令牌`，名字是 1 至 32 个小写字母、数字、横线、下划线，令牌至少 24 个字符；名字记进留痕和审核记录。写错了不启动）、`ADMIN_TOKEN`（旧的单个管理员令牌，继续可用，名字记为 `admin`；两个都不配则管理接口返回 503）、`ANTHROPIC_API_KEY`（助手用，不配则助手接口返回 503）、`MODEL`。

发邮件（验证码、登录通知、期限提醒）用的环境变量：`npm start` 和 `npm run remind` 都读这一组。

| 名称 | 默认 | 作用 |
|---|---|---|
| `MAIL_SENDER` | `outbox` | 发件方式。`outbox`：不联网，邮件留在库里的发件箱（`outbox` 表），本地开发和测试从 `GET /api/admin/outbox` 读；`console`：同上，另外打印到终端；`http`：向邮件服务商的 HTTP 接口发 POST（正式环境先用这个）；`smtp`：465 端口的 TLS 直连，AUTH PLAIN（对方的 EHLO 里只有 LOGIN 时用 AUTH LOGIN），不支持 STARTTLS |
| `MAIL_FROM` | 无 | 发件人，例如 `在留导航 <no-reply@example.jp>`。`http` 和 `smtp` 必填 |
| `MAIL_HTTP_URL`、`MAIL_HTTP_KEY` | 无 | `http` 用。请求是 `POST MAIL_HTTP_URL`，头 `Authorization: Bearer MAIL_HTTP_KEY`，JSON `{ from, to, subject, text, headers }`；返回 2xx 算成功 |
| `MAIL_HTTP_PRESET` | `generic` | 预留给具体服务商的请求格式，现在只有 `generic` |
| `SMTP_HOST`、`SMTP_PORT`（465）、`SMTP_USER`、`SMTP_PASS` | 无 | `smtp` 用 |
| `MAIL_TIMEOUT_MS` | 15000 | 一次发送最多等多久。发件箱里的邮件是一封一封占下再发的，每封占 10 分钟（这个值的 4 倍超过 10 分钟时按 4 倍），所以一轮发多久都不会被另一个进程重复发 |
| `APP_URL` | `http://localhost:PORT` | 提醒邮件里“打开在留导航”和退订链接用的地址，例如 `https://navi.example.jp`（`http://` 或 `https://` 开头，不带参数）。`MAIL_SENDER` 是 `http` 或 `smtp` 时必填 |
| `REMINDERS_ENABLED` | 关 | 设为 `1` 时 `npm start` 在进程里定时跑期限提醒。不开的话用 cron 跑 `npm run remind`，或者调 `POST /api/admin/reminders/run`；两种一起用也不会重复发 |
| `REMINDER_INTERVAL_MIN` | 60 | 定时器隔多少分钟看一次（1 到 1440）。轮到的时候还没到 `REMINDER_HOUR` 点，会另外等到那个点再跑一次，所以间隔设得再长（例如 1440）每天也至少跑一次 |
| `REMINDER_HOUR` | 9 | 日本时间几点以后才发（0 到 23）。只管进程里的定时器；`npm run remind` 什么时候跑由 cron 决定 |
| `TRUST_PROXY` | 关 | 设为 `1` 时，来源地址取 `X-Forwarded-For` 的最后一段（放在一层反向代理后面时开；直接对外时不要开，否则限流能被伪造的头绕过） |

服务商入驻（展示费和新咨询通知）用的环境变量，`npm start` 和 `npm run billing` 都读；写错了不启动并说明是哪一项：

| 名称 | 默认 | 作用 |
|---|---|---|
| `BILLING_PLANS` | 代码里的占位：士业 11000、其他 5500 | 展示费的价目表（日元/期，含税），JSON `{"regulated":11000,"other":5500}`，也可以再按类别写（例如 `"estate":8800`）；值是 0 到 1000000 的整数。`MAIL_SENDER` 是 `http` 或 `smtp` 时必填。价目表变了，新开的账单记下新的版本号 |
| `BILLING_PERIOD` | `month` | 现在只支持按自然月（日本时间） |
| `BILLING_ISSUE_DAYS` | 14 | 下一期的账单提前几天开（1 到 28） |
| `BILLING_FIRST_DUE_DAYS` | 14 | 批准时开的第一张账单，开出后几天到期（1 到 60） |
| `BILLING_GRACE_DAYS` | 7 | 已付款的那一期结束后，下一期没付还继续展示几天（0 到 60） |
| `BILLING_BANK_TEXT` | 无 | 振込先说明（银行、支店、账户类别、户名等），写进账单邮件和工作台。`MAIL_SENDER` 是 `http` 或 `smtp` 时必填 |
| `BILLING_INVOICE_REG_NO` | 无 | 适格请求书发行事业者的登记号（`T` 加 13 位数字）；填了的话账单和邮件里写登记号、10% 税率和税额 |
| `PROVIDER_NOTIFY_DELAY_MIN` | 5 | 来了第一条新咨询后等几分钟再发通知，这段时间的合成一封（0 到 1440） |
| `PROVIDER_NOTIFY_INTERVAL_MIN` | 60 | 同一家两封通知之间至少隔几分钟（1 到 1440） |

`MAIL_SENDER` 是 `http` 或 `smtp` 而设置不全（包括没有 `APP_URL`）、或者上面几个提醒的参数写得不对时，`npm start` 和 `npm run remind` 直接报错退出，并说明缺哪几项。期限的日期一律按日本时间的日历日算，和服务器的 `TZ` 无关。日志里只有数量和错误说明，不写邮件正文和收件地址（`console` 这种本地发件方式除外，它就是把邮件打印出来）。`createApp()` 不读这些变量（默认就是 `outbox`），所以测试和 `npm run e2e` 不会误发真邮件。

数据库：打开时先设 `busy_timeout`（10 秒）和 `secure_delete`，再建表。`npm start` 和 `npm run remind` 可以同时用同一个库文件，一方正在写时另一方等待；`npm run remind` 处理某个账号时撞上“库正忙”会再试两次，库打不开时报一行原因后以退出码 1 结束（cron 下一轮再跑）。删掉的行在库文件里用零覆盖，不留在空闲页里；这只管库文件本身，备份要按同样的期限另行清理，改动之前就存在的旧库文件要执行一次 `VACUUM` 才能清掉以前留下的空闲页。

## 接口

| 方法和路径 | 作用 |
|---|---|
| `POST /api/users` | 新建账号，body `{ "accept": "条款版本" }`（版本从 `GET /api/terms` 取），返回 id 和令牌（令牌只返回这一次）。之后的 `/api/users/:id/...` 都要带 `Authorization: Bearer 令牌` |
| `PUT /api/users/:id/state` | 网页端整体同步概况和完成记录 |
| `GET /api/users/:id`、`DELETE /api/users/:id` | 读取、删除自己的全部数据（删除时邮箱、验证码、其他设备的登录、发给这个邮箱的邮件、按它计的限流次数一并删掉） |
| `GET /api/terms` | 当前的条款版本 `{ version, changes, terms, privacy }`，`changes` 是给老用户看的“这次改了什么” |
| `POST /api/users/:id/consent` | 条款改版后重新同意，body `{ "accept": "当前版本" }`，返回账号。同意的还是旧版本的账号，除了 `GET`、`DELETE /api/users/:id`、这个接口，以及“收回”类的操作（`GET .../email`、`DELETE .../email` 和解除之前验证原邮箱的 `POST .../email/old`、`.../email/old/verify`（`action: "remove"`）、`PUT .../email/reminders` 关掉提醒），其余 `/api/users/:id/...` 一律返回 409 |
| `GET /api/users/:id/email` | `{ email, verified, remindOptIn }`，`email` 是打码的地址（`a***@example.com`）或 `null`；`remindOptIn` 是邮件提醒开没开 |
| `POST /api/users/:id/email/old` | 更换或解除之前验证原来的邮箱，第一步。body `{ "action": "change" }`（更换）或 `{ "action": "remove" }`（解除），向账号现在绑着的邮箱发 6 位验证码，返回 `202 { challengeId, expiresInSec: 600 }`。没有绑定邮箱时 409；刚用邮箱找回登录的设备 24 小时内 403 |
| `POST /api/users/:id/email/old/verify` | 第二步，body `{ "action", "challengeId", "code" }`，成功返回 `{ proof, expiresInSec: 900 }`：确认（只返回这一次），15 分钟内有效、只能用一次，只能用于这个账号、这种操作（`change` 的不能拿来解除，反过来也不行）、验证时绑着的那个邮箱。失败是同一个 422 |
| `POST /api/users/:id/email` | 绑定邮箱的第一步，body `{ "email": "...", "consent": true, "proof"? }`（账号上已经绑着邮箱时必须带 `action: "change"` 的确认，不带或确认不对是 403，不发信），返回 `202 { challengeId, expiresInSec: 600 }` 并向这个邮箱发 6 位验证码。邮箱已经绑在别的账号上时返回的内容一样，但发过去的是一封说明，没有验证码 |
| `POST /api/users/:id/email/verify` | 第二步，body `{ "challengeId", "code", "remindOptIn"?, "proof"? }`（换绑时同样要带确认，在换绑的同一个事务里用掉；确认不对是 403，新邮箱的验证码不会因此用掉），成功返回 `{ email, verified, remindOptIn }`（换绑时替换原来的邮箱，邮件提醒随之关闭，原来的邮箱收到一封“邮箱已经更换”的告知；带 `remindOptIn: true` 时绑定后直接打开邮件提醒）。验证码方面的任何失败都是同一个 422“验证码不对或已过期”。账号上已经绑着邮箱、而这台设备是 24 小时内刚用邮箱找回登录的，这一步和上一步都是 403 |
| `DELETE /api/users/:id/email` | 解除绑定，body `{ "proof" }`（`action: "remove"` 的确认，不带或不对是 403，什么都不改；没有绑定邮箱时不用带），删掉邮箱、没用完的验证码、发给它的邮件记录和按它计的限流次数，并向原来的邮箱发最后一封告知（发出后地址不留），返回 204。账号和已有的登录不变。刚用邮箱找回登录的设备 24 小时内调它是 403 |
| `PUT /api/users/:id/email/reminders` | 邮件提醒的开关，body `{ "on": true }` 或 `{ "on": false }`，返回 `{ remindOptIn }`。默认关；没有绑定邮箱时 409 |
| `GET /api/unsubscribe?t=令牌`、`POST /api/unsubscribe?t=令牌` | 提醒邮件里的退订链接，不用登录，返回网页。GET 只显示确认页，不改任何东西；POST 才关掉邮件提醒（请求体不解析，邮件客户端的一键退订也走这里）。令牌不存在、已经退订过，返回的页面都一样 |
| `POST /api/auth/recover` | 用邮箱找回账号的第一步，不用登录，body `{ "email" }`。不管邮箱有没有绑定过，都返回 `202 { challengeId, expiresInSec: 600 }`；只有绑定过的才真的发验证码 |
| `POST /api/auth/recover/verify` | 第二步，body `{ "challengeId", "code" }`，成功返回 `{ id, token }`：这台设备的新令牌（只返回这一次），原来设备的令牌不变，并向邮箱发一封“有新设备登录”的通知。失败是同一个 422 |
| `GET /api/users/:id/sessions`、`DELETE /api/users/:id/sessions` | 登录着的设备 `[{ createdAt, lastUsedAt, via, current }]`（`via`：`signup` 注册时的令牌、`recover` 邮箱找回）；DELETE 让发请求的这台以外的设备全部退出，返回 204 |
| `PATCH /api/users/:id/profile` | 修改概况（身份、日期、出国记录等） |
| `PUT /api/users/:id/tasks/:nodeId/done` | 标记任务完成或撤销，body `{ "done": true }` |
| `GET /api/users/:id/plan`、`/reminders`、`/advice`、`/pr-check` | 路线、提醒、判断、永驻体检。`/reminders` 每条是 `{ date, text, tag, src }`：`date` 是日本时间的日历日，`YYYY-MM-DD` 的文字（不是时刻，不要按时区换算）；`src` 是事件期限的依据 `{ law, title, url, more? }`（法条、官方页面，`more` 是另外要看的页面），其他提醒为 `null` |
| `POST /api/users/:id/chat` | 和助手对话，body `{ "message": "...", "history": [] }`。返回 `{ text, category, toolCalls, draft, history }`：`history` 原样保存、下一轮带回（服务器已按轮裁剪到最多 20 条）；`draft` 是助手准备的咨询草稿或 `null`，助手自己不能发送咨询。历史不合规则、或历史里有疑似敏感号码时返回 422，说明以 `history` 开头（清空历史后重试），提问太频繁返回 429（带 `retry-after`） |
| `GET`、`POST /api/users/:id/inquiries` | 发给服务商的咨询。必须带 `consent: true` 和 `providerIds`（最多三家）。这是唯一能把咨询发出去的途径 |
| `GET /api/nodes`、`/api/nodes/:id` | 节点资料 |
| `GET /api/options/:topic` | 选方案。topic：route、degree、points、phone、drive、company、budget |
| `GET /api/providers/categories` | 服务类别和收费方式：`{ key, name, what, regulated, feeModel, promoted }`。所有类别都只付固定的展示费；`feeModel` 士业是 `fixed_listing`，其余是 `affiliate_disclosed`（只表示名单上标“含推广”，名字为兼容保留，不表示有佣金），`promoted` 为真的在名单上标“含推广” |
| `GET /api/providers?category=` | 名单上展示的服务商（在架，并且展示费已付到今天；见“服务商入驻”）。公开名称、所属会、登录番号、事务所地址、收费说明、区域、语言，联系邮箱不公开 |
| `GET`、`POST /api/users/:id/events`，`DELETE .../events/:eid` | 会产生期限的事件 |
| `GET /api/admin/providers`、`PUT /api/admin/providers/:id/active` | 管理员看全部服务商（展示状态、展示到哪一天、最近一张账单、打码的联系邮箱）和上架、下架（带管理员令牌）。下架时令牌立即作废，排队中的新咨询通知和账单邮件不发；重新上架后要重新领取令牌 |
| `POST /api/admin/providers` | 管理员直接入驻：会把令牌返回给管理员，所以只在 `createApp({ allowDirectProvider: true })` 时有（测试和端到端用，不读环境变量），正式环境 404。和入驻申请同一套检查：登录番号的格式和所属会（`licenseBody`）、名称、地址、收费说明、区域、语言没有保证类用语、过敏感号码过滤；收费方式按类别定，请求里的 `feeModel` 和它不一致就 422 |
| `GET /api/provider-terms` | 服务商条款的版本 `{ version, url }` |
| `POST /api/provider-apply/code`、`POST /api/provider-apply` | 入驻申请：先向联系邮箱发验证码（202，返回内容不看邮箱的情况），再带 `{ challengeId, code, category, name, address, licenseNo?, licenseBody?, feeNote, area, langs, agree: 条款版本 }` 提交，201 `{ ref }` 并发“已收到申请”。同一邮箱已有审核中或等待修改的申请 409；每个来源地址每天最多提交 5 次 |
| `POST /api/provider-apply/open`、`PUT`、`DELETE /api/provider-apply/:ref` | 查看或修改：验证码对了返回这个邮箱最近的一份申请和确认 `proof`（30 分钟内有效）；凭确认在“要求修改”时重新提交（回到审核中）或撤回 |
| `POST /api/provider-claim/code`、`POST /api/provider-claim` | 服务商用联系邮箱领取令牌：只有已批准、在架的服务商的联系邮箱才真的收到验证码，其他邮箱返回一样（排一行占位）；验证码对了返回 `{ token }`（只返回这一次），旧令牌立即失效，联系邮箱收到“令牌已重新发放”的告知 |
| `GET`、`POST /api/provider-unsubscribe?t=` | 新咨询通知邮件里的退订链接，规则和 `/api/unsubscribe` 一样（GET 只显示确认页，POST 才关） |
| `GET /api/admin/applications[?status=]`、`GET /api/admin/applications/:id` | 入驻申请（邮箱打码，带核对记录、去哪里核对和 `reviewKey`：管理员看到的版本） |
| `POST /api/admin/applications/:id/approve` | 批准，body `{ reviewKey, licenseCheck: { method, checkedOn, note? } }`（`reviewKey` 是打开申请时看到的版本，必填；之后申请人又改过就 409，要重新打开再审，核对记录不会记到没人看过的登录番号上；士业和不动产必填；`method` 是 `association_search`、`certificate`、`phone_association` 之一，核对日期不能晚于今天）。核对人、核对时间由服务器记。一个事务里建服务商、第一张账单，发批准邮件（领取令牌的步骤和账单），返回 `{ providerId, invoiceId }`，没有令牌 |
| `POST /api/admin/applications/:id/reject`、`.../request-changes` | 拒绝 `{ reviewKey, reason }`、要求修改 `{ reviewKey, message }`（`reviewKey` 和批准一样），5 至 500 字，过敏感号码过滤，写进发给申请人的邮件 |
| `GET /api/admin/invoices[?status=]`、`POST /api/admin/invoices/:id/paid`、`.../void` | 账单；标记已付款 `{ paidOn, note? }`（带 `amount` 是 422），作废 `{ reason }` |
| `POST /api/admin/billing/run` | 现在跑一轮展示费和新咨询通知并发件，跑多少次都不重复 |
| `POST /api/billing/webhook/:method` | 在线支付的回调，留着以后接；现在 404 |
| `POST /api/admin/reminders/run` | 现在就跑一轮期限提醒并把到时间的邮件发掉（带管理员令牌），返回 `{ users, mails, items, errors, sent, failed, dropped }`，只有数量。运维补跑和端到端检查用，跑多少次都不会重复发 |
| `GET /api/admin/outbox?status=&to=` | 发件箱（带管理员令牌；没配 `ADMIN_TOKEN` 时 503）。本地发件方式（`outbox`、`console`）下带正文，开发和端到端检查从这里读验证码；`http`、`smtp` 下只有状态，不带正文，收件地址打码 |
| `GET /api/provider/me`、`/api/provider/inquiries`，`POST .../inquiries/:id/reply`，`PUT .../inquiries/:id/status` | 服务商查看和回复咨询（带服务商令牌）。`me` 另有 `{ listed, listedUntil, notify, termsVersion, contact }`（`contact` 是打码的联系邮箱）。没在名单上展示时工作台照常能用。回复过敏感号码过滤，也不能有保证类用语（“不能保证结果”这种否定的提醒可以写），被拒时工作台显示服务器的说明 |
| `PUT /api/provider/me/notify`、`GET /api/provider/invoices` | 新咨询通知的开关 `{ on }`；自己的账单（带振込先和参考编号） |

## 写进代码的合规规则

- 不收集个人编号、护照号、银行账号和卡号：接口遇到这类字段直接拒绝；自由文本经过同一个过滤函数，规则见下面“敏感号码过滤”。
- 发给服务商的咨询必须有用户的明确同意。助手只能准备草稿（`create_inquiry` 工具不写库、不发送），草稿和接口用同一套校验（摘要去掉首尾空白后 5 至 2000 字、节点有效、同一类别在架的服务商最多三家且不重复、敏感号码过滤）；发送只能由用户在页面上确认后调 `POST /api/users/:id/inquiries`。
- 士业（行政书士、税理士、社会保险劳务士、司法书士）只收固定展示费，不按成交抽成；非士业的推广要标明。规则见下面“服务商入驻”。
- 助手不制作交给官方的文书，不对个别的在留和税务情况下结论，不作任何保证。
- 用户可以删除自己的全部数据；每次写入都有留痕。删除在一个事务里完成，并把留痕表里这个用户的 id 和细节（改了哪些字段、咨询 id、发给了哪家服务商）清空，只留下“某时发生过某动作”。
- 日期一律要求 `YYYY-MM-DD` 且日历上存在（`2026-02-30` 拒绝），概况、出国记录、事件、助手工具共用 `src/validate.js` 的 `isDate`。
- 限流（内存计数，单进程）：助手每个账号 10 分钟 20 次、24 小时 200 次；新建账号每个来源地址 1 小时 30 个。超过返回 429。放在反向代理后面时要开 `TRUST_PROXY=1`，否则来源地址都是代理。
- 邮箱绑定和找回（`test/auth-email.test.js`，2026-11-27 复查后补的规则在 `test/hardening.test.js`）：
  - 绑定必须先用验证码证明邮箱是自己的，并明确同意（`consent: true`）；一个账号一个邮箱，一个邮箱一个账号。邮箱转成小写、去掉首尾空白后按原文存在单独的表里（发信要用），最长 254 个字符。写法（`src/validate.js` 的 `normalizeEmail`）：@ 前面是英文字母、数字和 `. _ + - ' ! # $ & * / = ? ^ { | } ~` 及反引号，最长 64 个字符，不能以点或横线开头，点可以连着写、可以紧挨着 @（日本手机运营商发过 `a..b@docomo.ne.jp`、`abc.@ezweb.ne.jp` 这样的地址）；不接受 `%`、引号、空格、尖括号、换行；@ 后面至少两段，最后一段是两个以上的字母（`a@1.2`、`a@b.c` 不收）。中文域名不支持。
  - 验证码：6 位数字，库里只存 `sha256(challengeId:验证码)`，10 分钟失效，只能用一次，错 5 次作废（次数记在这一个验证码上）。绑定：同一个账号重新发送后，自己的旧验证码作废；别的账号对同一个邮箱索取不影响你的。找回：重新发送不作废旧的（找回不用登录，谁都能对着一个邮箱点发送；新的一发就作废旧的话，知道邮箱的人就能让本人的验证码一直失效），各自有效到过期，用掉一个后同一邮箱其余的一并作废。绑定用的验证码只能由发起的那个账号用，不能拿去找回，反过来也不行。
  - 限流（次数存在库里，重启不清零，超过返回 429 和 `retry-after`；被限的请求不发邮件）。发验证码：找回按（来源地址，邮箱）、绑定按（账号，邮箱）各 1 分钟 1 次、1 小时 5 次、24 小时 10 次——各人算各人的，别人对着你的邮箱点发送耗不掉你的次数；每个邮箱合计 1 小时 12 次、24 小时 30 次（绑定和找回分开计），管住发到同一个邮箱的邮件总量；另外每个来源地址 1 小时 10 次，每个账号 1 小时 5 次（绑定）。核对验证码：每个来源地址 1 小时 30 次，每个账号 1 小时 30 次（绑定），每个验证码错 5 次作废；不按邮箱合计（合计的话谁都能把它耗光，让本人验不了）。限流表里是来源地址、邮箱、账号的哈希，不是原文，留 24 小时；解除邮箱、删除账号时按它记的次数一并删掉。已知的余地：有四五个以上来源地址的人仍然能把“每个邮箱合计”的次数用完，让这个邮箱在窗口内（最长 24 小时）收不到新的验证码；合计上限去掉的话，别人又能往这个邮箱里灌邮件，这里选了保护邮箱。原来登录着的设备不受影响。
  - 不透露邮箱是否注册过：找回时邮箱绑没绑定过，状态码、响应内容的形状和长度、数据库的提交次数都一样（没绑定过的也存一条永远验不过的验证码），邮件在响应发出之后才发；发送那一步自己也要写库、会占住进程几毫秒，所以没绑定过时也排一行占位（`outbox` 表里 `kind='pad'`，不是邮件，不出现在发件箱接口里），发送那一步对它做同样多的读写再删掉，紧跟着的下一个请求的快慢因此也分不出来（用 `http`、`smtp` 真实发信时，发起网络请求本身的那一点开销仍然只有绑定过的才有）；绑定时邮箱是否已被别的账号占用也一样。接口从不返回完整的邮箱，只返回打码的。
  - 找回账号给新设备发新令牌（库里只存哈希，一个账号最多留 10 个），原来的设备不掉线；同时给邮箱发“有新设备登录”的通知；用户可以看到有几台设备登录着，并让其他设备退出。
  - 换绑和解除要先验证原来的邮箱（负责人 2026-11-27 定的规则，`test/email-change.test.js`）：从任何设备都一样。更换 = 原来的邮箱收验证码（`POST .../email/old`，`action: "change"`）→ 拿到确认 → 新邮箱收验证码 → 带着确认核对新邮箱的验证码；解除 = 原来的邮箱收验证码（`action: "remove"`）→ 带着确认 `DELETE`。验证码的规则和别的验证码一样（只存哈希、10 分钟、只能用一次、错 5 次作废、只认发起的账号，重新发送后同一账号同一种的旧验证码作废），和绑定、找回的验证码互不通用。确认是 32 字节的随机值，库里只存哈希（放在验证码表里，`purpose` 是 `ok-change`、`ok-remove`），15 分钟有效、只能用一次；邮箱换掉、解除、账号删掉时随验证码一起删掉，验证时绑着的邮箱已经不是现在这个的也作废。限流：发验证码按（账号，原邮箱）1 分钟 1 次、1 小时 5 次、24 小时 10 次，每个邮箱合计 1 小时 12 次、24 小时 30 次，另外和绑定共用每个来源地址 1 小时 10 次、每个账号 1 小时 5 次；核对按来源地址、按账号各 1 小时 30 次。这一步只发给账号自己绑着的邮箱，不涉及“这个邮箱有没有注册过”。
  - 原来的邮箱收不到信了（邮箱停用、忘了密码）：没有绕过的办法，换不了也解除不了，客服也不替人改——账号是匿名的，客服能核对的东西不会比“能收到这个邮箱的信”更可靠，开一个人工通道就是最弱的一环。出路：照常用这个账号（邮件提醒随时可以关，关掉不需要验证），或者删除账号重新开始（邮箱随之释放，可以绑到新账号上）。页面上“账号和邮箱”里写着这一条；条款第 7 条、隐私政策第 7 条也写了（两份草案的版本号没改：2026-11-27 当天上线前改的，还没有真实用户；已经有用户的部署要按下面“条款版本”的规则改版本号）。
  - 换绑和解除：原来的邮箱一定会收到一封告知（“邮箱已经更换”“邮箱已经解除”，不写新邮箱是什么；排着队还没发出去的“新设备登录”通知也照发），这几封在发件箱里记为 `last`，发出或放弃后立即清掉地址和正文。刚用邮箱找回登录的设备，24 小时内不能更换或解除已经绑着的邮箱（连验证原邮箱这一步也是 403，说明还要等多久）：这是负责人 2026-11-27 确认保留的规则，和上面“先验证原来的邮箱”叠在一起用——找回本身也只要邮箱的一次验证码，冷静期让本人收到“有新设备登录”的通知后，有时间在自己的设备上让它退出，或者再用邮箱找回一次把它退出。注册时的设备没有冷静期（换绑、解除照样要验证原来的邮箱），“让其他设备退出”不受限。告知邮件里写明更换、解除时输入了发到这个邮箱的验证码，不是本人的话先改邮箱密码；更换的告知不再叫人“把邮箱换回来”（换回来要那个新邮箱的验证码，做不到），而是说明要彻底断开得删除账号。
  - 留痕只记动作（`email.bind`、`email.remove`、`email.confirm`（验证过原来的邮箱，只记 `{ action }`）、`session.recover`、`session.revoke`、`consent.renew`），从不写邮箱、验证码、令牌。
  - 邮件都先进发件箱再发：发不出去的按 1 分钟、5 分钟、30 分钟、2 小时、12 小时重试，之后记为 `failed`。发件箱里的邮件一封一封占下再发（`store.claimNext`），两个进程一起发也不会把同一封发两次。验证码邮件：验证码 10 分钟过期，到那时还没发出去的不再发，记为 `dropped`；正文在真实发信时发完就清掉（连同收件地址），本地方式下 1 小时后清掉；其他邮件 30 天后清掉地址和正文。没绑定邮箱的账号解除邮箱、删除账号时不会碰别人的发件记录。验证码记录失效 24 小时后删除。验证码和通知邮件里不放链接，验证码不放在标题里。存进库里的发送错误说明先把像邮箱的东西换掉。
- 期限提醒邮件（`src/scheduler.js`，`test/reminders.test.js`、`test/hardening.test.js`）：
  - 自愿：默认关，只有绑定并验证过邮箱的账号能开（`PUT .../email/reminders`，或页面上“账号和邮箱”“提醒”页里的开关）；换绑邮箱后自动关。每封邮件带退订链接（每个邮箱一个 32 字节的随机令牌，凭它只能退订）和 `List-Unsubscribe`、`List-Unsubscribe-Post` 两个头；退订不用登录，要点一下确认页上的按钮（GET 不退订，防邮件服务预先打开链接）。
  - 发哪些：只发有确定日期的提醒，标签是 法定期限、在留、事件、银行、每年。其中真正的期限由引擎标出（`dl`：法定期限、事件期限、在留期满日、确定申告截止），邮件里写“今天到期”“明天到期”；其余是该开始准备或该留意的日子（在留更新的几个节点、入境满 6 个月去银行、住民税缴款单、年末调整），只写“今天”“明天”“还有 N 天”。一封里全是期限时标题是“有 N 件事今天到期／明天到期／快到期限”，否则是“有 N 件事要留意”。日期总是“今天”或每月滚动的那些（“现在是年末调整的时期”、路线、习惯、方案订阅、每月的年金、邮箱示例）不发。
  - 什么时候发：到期前 7 天、前 1 天、当天各一封，按日本时间的日历日算。还剩 2 到 6 天才第一次轮到（刚打开提醒、刚记下事件、停机几天）时补发一封“前 7 天”那一档的，写的是实际还剩几天；错过的档只记账不补发；过了期不发。同一位用户同一轮到期的几件事合成一封。
  - 不重复发：`reminder_sends` 表的主键是（账号，提醒，到期日，档）。每一档先占一行，占到了才排进发件箱，占位和排队在同一个事务里，所以重启、反复跑、进程里的定时器和 `npm run remind` 同时跑，同一档都只有一封。“提醒”用 `sha256(标签|文字)` 表示，文字或日期变了就是新的提醒。
  - 办完、删掉、改了日期的不发：每一轮都用引擎重新算；已经排了队的邮件在真正发出之前再算一次，只留仍然有效、仍在当初那一档的事项并按当时的天数重写正文，一件都不剩或者用户已经退订、换了邮箱，就不发（发件箱里记为 `dropped`，正文和地址清掉）。用户关掉提醒、退订、换绑或解除邮箱时，还没发出去的那几档从账本里删掉而不是记成 `dropped`：马上又打开的话，这一档还能重新排上；已经发出去的不会重发。
  - 发不出去：和其他邮件一样按 1 分钟、5 分钟、30 分钟、2 小时、12 小时重试，之后记为 `failed`，不再发；账本里每一档的状态是 `queued`、`sent`、`failed`、`dropped`、`skipped` 之一。
  - 邮件内容（简体中文）：日期、还剩几天、这件事的说明、依据和官方页面链接（规则里有的才带，只接受 `https://`）、打开应用的链接（`APP_URL/#reminders`）、退订链接、“只供参考”的说明。不写姓名、在留资格的类型、账号编号和没到期的事项。页面上按在留资格写得不一样的事件期限（换工作后的所属机关届出、离婚后的配偶者届出），邮件里用不分在留资格的写法和依据（`src/engine.js` 的 `EVRULES` 里每条规则的 `mail`、`msrc`；没有 `mail` 的规则本身就不分），所以同一件事不同身份的人收到的邮件一字不差；新增规则时文字里带了在留资格的名称，`test/hardening.test.js` 会失败。
  - 留痕只记 `email.remind`（开或关）和 `email.unsubscribe`，不写邮箱和令牌。删除账号时账本一并删除。
- 条款版本（`src/server.js` 的 `TERMS_VERSION` 和 `TERMS_CHANGES`，现在是 `2026-11-27`）：改了条款或隐私政策的文字就改版本号和“这次改了什么”。同意的是旧版本的账号，重新同意之前服务器只让读取和删除自己的数据，以及查看绑定的邮箱、关掉邮件提醒、解除邮箱（连同解除之前验证原来的邮箱；验证“更换”不放行。不同意新条款的人也要能让我们停发邮件、删掉邮箱；提醒邮件在他关掉之前照常发）；网页下次打开时弹出“条款有更新”，可以同意并继续，或者直接删除账号。

- 申请：联系邮箱先收验证码（`papply`，规则和找回账号的验证码一样：只存哈希、10 分钟、错 5 次作废、重新发送不作废旧的；限流按（来源地址，邮箱）和每个邮箱合计分别计，另外每个来源地址），再提交。收费方式不看请求：士业固定为 `fixed_listing`，其余为 `affiliate_disclosed`。两种都只付同样的固定展示费，不按咨询数、成交或结果付费；`affiliate_disclosed` 只表示“名单上标明含推广”（名字是早先定的，为了兼容旧数据没有改，不表示有佣金）。名单、助手的名单和草稿卡片上的“含推广”都按类别算（非士业一律标），不看库里存的值。所有自由文字（名称、地址、收费说明、区域、语言、管理员写的理由和备注）过敏感号码过滤；名称、地址、收费说明、区域、语言（入驻申请、管理员直接入驻、老服务商迁移）和服务商的回复不能有保证类用语（`src/validate.js` 的 `assertNoClaims`：合格保证、包过、保证、必过、确保、一定能、绝对、最安、日本一、No.1、100%，简体、繁体、日文写法都算；先做 NFKC，再去掉零宽字符和空白，所以全角、“包 过”“包​过”也算；“不保证”“无法保证”“不能确保”“不一定能”这种否定的说法先去掉再判断）。
- 登录番号的格式（`src/validate.js` 的 `LICENSE_RULES`，NFKC 后去掉空白和「第」「号」；只防打错，不算核实）：行政书士 8 位数字、税理士 1 至 6 位、社劳士 8 位、司法书士 1 至 5 位，这四种还要填所属会（`…行政書士会` 等）；不动产要填宅建业免许番号（`大阪府知事(3)12345`、`国土交通大臣(1)9876`）；其他非士业可以填 13 位法人番号（校验位要对）。士业法人用负责人个人的登录番号。
- 审核：管理员对照所属会的检索核对后批准，士业和不动产必须写核对方式和核对日期，核对人（管理员令牌的名字）、核对时间（服务器时间）由服务器记，存在申请表里，不进留痕。拒绝、要求修改都发邮件。被拒绝、撤回的申请 90 天后整行删掉。后台没有修改类别、收费方式、登录番号、金额的接口：要改只能由服务商在“要求修改”时重新提交，再审核一次。
- 令牌：批准时不发令牌（库里是谁也用不了的值），服务商在工作台用联系邮箱的验证码领取（`pclaim`），只显示一次；重新领取作废旧令牌；任何邮件里都没有令牌，管理员也看不到。下架时令牌换成谁也用不了的值，重新上架后要重新领取。
- 展示费（`src/billing.js`）：按自然月（日本时间）的固定金额，分士业和其他两档，金额只按价目表（`BILLING_PLANS`），请求里的金额一律拒绝；账单里存开票时的金额和价目表版本。批准时开第一张账单（本期，`BILLING_FIRST_DUE_DAYS` 天后到期，当月整月收费，不按天折算）；下一期的账单提前 `BILLING_ISSUE_DAYS` 天开，期限是下一期开始的前一天。参考编号形如 `ZN2612-7KQ4MX`（去掉了 0、O、1、I、L）。付款期限前 7 天、前 1 天、过期第二天各提醒一次（去重账本 `invoice_reminders`，跑多少遍都只有一封；错过的档不补发）。
- 名单上展示的条件（算出来，不存，`store.providerListing`）：在架，并且今天落在一段“已付款的覆盖”里。覆盖按账单的期间先后接起来（作废的不算）：已付款的一期接得上前一段（开始日不晚于前一段结束的第二天）就把这段延到 本期结束 + `BILLING_GRACE_DAYS` 天，接不上就另起一段——所以下架再上架、作废了中间一期、拖欠了几期之后，付了当期就展示，不会被以前的旧覆盖挡住；已开出还没付的下一期只能接在已付款的一段后面，把这段延到它的 付款期限 + `BILLING_GRACE_DAYS` 天（月底批准、迁移或定时任务跑晚了，下一期的期限落在覆盖结束之后时，期限没过不下架）。没付过款的那一段不展示（批准了没付款的不上名单）。过了还没付下一期的自动不展示，并在同一天告知一次（条件同样是 付款期限 + 宽限天数 < 今天；展示过的才告知）；这时先不开再下一期的账单，付了或作废之后再开。不展示时工作台照常能用（回复已有的咨询、看账单），用户也不能给它发新咨询。管理员标记已付款（入账日不能晚于今天）后立即展示。作废的账单不能再标记已付款，作废后这一期可以重新开。
- 收款方式可以替换：现在只有人工确认的银行转账（`manual_bank`：振込先 + 参考编号）。以后接刷卡、在线支付时实现 `{ name, createCheckout(inv) -> { payUrl }, verifyWebhook(req, rawBody) }`，回调接口 `POST /api/billing/webhook/:method` 已留出（现在 404）。
- 新咨询通知（`src/notifier.js`）：新咨询和“要通知”的记号在同一个事务里写；第一条之后等 `PROVIDER_NOTIFY_DELAY_MIN` 分钟，把这段时间的合成一封，同一家两封之间至少隔 `PROVIDER_NOTIFY_INTERVAL_MIN` 分钟。邮件里只有数量、类别、工作台链接和关闭通知的链接（带 `List-Unsubscribe`），没有咨询内容、节点、用户编号；发件箱里这几封的 `user_id` 是空的，和用户删账号互不影响。发之前再看一次：下架、关了通知、换了邮箱、这段时间的咨询数变成 0（用户删了账号），都不发。
- 老服务商（这套机制之前直接入驻的，没有补充资料）：`createApp` 建好时就迁移（`npm run billing` 和每一轮定时任务也会先查一遍），不等第一轮定时任务，期间不会被当成没付款而不展示。迁移时按入驻申请的规则查资料（类别、登录番号的格式和所属会、名称和收费说明等的保证类用语），收费方式按类别改正。过了的记为 `legacy`，补一张免费的当期账单（`method` 为 `migration`），下一期起照常收费；没过的记为 `legacy-hold`：不展示、不开账单，令牌照常能用（可以回复以前的咨询），管理后台显示“老服务商，资料没过检查”。老服务商没有登记过所属会，所以士业都会落在 `legacy-hold`；要重新展示，请他们用联系邮箱走入驻申请（经审核和核对登录番号后是一家新的服务商），批准后把旧的那家下架。留痕 `provider.migrate` 只写编号和问题的代号（`category`、`license`、`claims`）。老服务商没有联系邮箱，收不到账单和提醒，下一期没付款就会在 付款期限 + 宽限天数 之后不展示。
- 留痕只写编号、动作和管理员名：`papply.submit`、`papply.resubmit`、`papply.withdraw`、`papply.approve`（带 `by`、核对方式）、`papply.reject`、`papply.changes`、`provider.claim`、`provider.revoke`、`provider.notify`、`provider.hidden`、`provider.migrate`、`invoice.issue`、`invoice.paid`、`invoice.void`（带 `by`）。邮箱、验证码、令牌、理由原文、核对备注都不进留痕。
- 定时：`npm start` 每分钟看一次新咨询通知，每小时跑一轮展示费（启动 5 秒后先跑一次）；也可以由 cron 跑 `npm run billing`，或调 `POST /api/admin/billing/run`，几种一起用不会重复发。

## 网页端的行为

`web/index.html` 在本服务器上打开时按下面的规则工作，每一条都在 `e2e/browser.js` 里有检查。

- 账号：同意条款后才建账号（或在同一个对话框里用邮箱找回已有的账号），账号（id 和令牌）存在浏览器的 localStorage 里。打开页面读取账号时，只有服务器明确回答 401 或 404 才丢掉本机的账号并重新走同意流程；连不上、5xx、429 都保留账号，页面顶部显示状态和“重试”，并按 2 秒起、每次加倍、最长 60 秒自动重试。建账号失败时同意对话框不消失，把原因显示出来。
- 保存：修改先写本机，再发 `PUT /state`（同一时间只发一个请求）。没存上时记下“有修改未保存”的标记（localStorage 的 `zairyu-unsaved`），顶部显示提示，自动重试（同样的退避，浏览器恢复联网时也立刻重试）。带着这个标记再打开页面时，以本机的内容为准发给服务器，不用服务器的旧内容覆盖本机。422 这类重试也没用的失败只提示，不反复重试。
- 邮箱和设备：“我的情况”里有“账号和邮箱”。绑定要填邮箱、勾选同意、再填邮件里的验证码；绑定后只显示打码的地址，有“更换邮箱”和“解除绑定”两个按钮，没有直接填新邮箱的框：点“更换邮箱”后验证码发到现在绑着的邮箱，填对了（“确认是我”）才出现新邮箱的输入框、同意的勾和“发送验证码”，再填新邮箱的验证码“确认更换”；点“解除绑定”先确认，再填发到现在这个邮箱的验证码，对了就解除。每一步都可以取消；确认过期（15 分钟）时页面回到开头并显示服务器的说明。下面有一段“原来的邮箱收不到信了？”说明没有绕过的办法、可以照常用或删除账号重新开始。刚用邮箱找回登录的设备 24 小时内点这两个按钮，页面显示服务器的说明，不发验证码。绑定后那里和“提醒”页各有一个“邮件提醒”的勾（同一个设置，默认不勾），文字写明前 7 天、前 1 天和当天各一封、有官方页面的会带上链接；没绑定邮箱时“提醒”页说明要先去绑定。连着服务器时不显示“授权自动获取”里演示用的那个“邮件提醒”。下面列出登录着的设备，多于一台时可以“让其他设备退出登录”（先确认）。同意对话框里有“已有账号？用邮箱找回”：不管邮箱有没有绑定过，发送后的提示都一样；验证码对了就换成找回的账号（这台设备拿到新令牌，本机缓存的别的账号的内容不带过来）。本机的登录失效（401）时，对话框里说明原因并提示可以用邮箱找回。
- 条款改版：读回来的账号同意的版本和 `GET /api/terms` 的不一样时，先弹出“条款有更新”（写明这次改了什么），点“同意并继续”后调 `POST /consent` 才进入；也可以在那里直接删除账号。
- 示例和删除：有账号时没有“恢复示例”（它只在不连服务器的本地演示里出现），“从零开始”要先确认。“我的情况”里有“删除我的账号和全部数据”：确认后调 `DELETE /api/users/:id`，成功（或服务器上已经没有这个账号）后清空 localStorage 里的账号、缓存和未保存标记，回到同意对话框；删除失败时什么都不清，并说明没删成。
- 助手：`history` 原样保存、原样带回，页面不裁剪。历史被拒（422，说明以 `history` 开头）时清空历史自动重试一次；连续两次其他失败或 413 时清空历史，避免卡死；敏感号码（422）和限流（429）显示服务器的说明，历史保留，原话放回输入框。
- 助手的咨询草稿：接口返回 `draft` 时，对话里出现一张卡片，写明发给哪几家、要发送的全文，同意的勾默认不勾。用户勾选并点“发送给服务商”后，页面才调 `POST /inquiries`（`consent: true`，摘要就是卡片上显示的文字）。不点就什么都不发。
- 咨询申请表：页面上显示的就是要发出去的全文（咨询内容、方式、情况说明），发出去的也是这段文字。选的服务商、类别、文字或情况说明一变，同意的勾就取消；没有选中的服务商时表单收起；发送失败后要重新勾。
- 助手的名单和草稿：`suggest_providers` 和 `create_inquiry` 的结果都带 `disclosure`（服务商付固定的展示费；非士业另说明含推广），系统提示第 8 条要求助手照着说，并给 `promoted` 的服务商标“含推广”。草稿卡片上每家非士业的后面有“含推广”，下面固定写着展示费的说明。`create_inquiry` 和 `POST /inquiries` 一样只认此刻在名单上展示的服务商（批准了没付款的不行）。
- 被服务器拒绝的内容（疑似敏感号码、长度不对等）：咨询表、草稿卡片、助手、事件、服务商回复都把服务器返回的中文说明显示给用户，输入的内容保留。
- 事件期限：提醒里每条事件期限带法条和官方页面的链接（只接受 `https://` 的地址；高度专门职换工作带契约机关和活动机关两个页面）。短期滞在的人记录孩子出生也有出生届和在留资格取得的期限。记录的事件按当前身份没有登记到期限时，只提示“这里没有登记到对应的期限，请以入管厅或区役所的说明为准”，不说“没有法定期限”；助手的提示词和 `add_event` 的返回也是这个口径。
- 服务商入驻：申请页（`web/provider-apply.html`）先验证联系邮箱，再填申请（选了士业或不动产才出现登录番号和所属会的栏），要勾同意服务商条款；被拒的原因（保证类用语、敏感号码、格式）显示服务器的说明；提交后显示申请编号。“查看或修改申请”用邮箱的验证码打开，被要求修改时可以改后重新提交，审核完之前可以撤回。管理后台（`web/admin.html`）的令牌只在内存里，士业不选核对方式批准不了（显示服务器的说明）。工作台里“第一次使用或令牌丢了”用联系邮箱领取，新令牌只显示一次、不存进浏览器；登录后显示是否在名单上展示、展示到哪一天、账单（振込先和参考编号）、新咨询通知的开关。首页名单上方固定写着展示费的说明，每家显示所属会和事务所地址，下面有“服务商申请入驻”的链接。
- 服务商工作台：只有 401 才说“令牌不对，或账号已停用”，连不上和服务器出错分开说明；登录成功但名单读不出来时在名单上方提示并可重试；发送回复、结束咨询失败都在那一条下面说明原因；没发出去的回复草稿在名单刷新后还在。
- 页面里不使用 `innerHTML`：来自服务器、用户、服务商和助手的文字一律用 `textContent` 放进去。

## 端到端检查

```
npm run e2e
```

`e2e/run.js` 在空闲端口上起一个服务器（临时目录里的新数据库），跑 `e2e/browser.js`，跑完关掉并删掉数据库。网页端的行为只有这里在检查，`npm test` 不跑它（`npm test` 只保证网页内嵌的规则和引擎一致），所以改了 `web/` 之后和发布之前都要跑。playwright 不在默认的模块路径上时用 `PLAYWRIGHT_PATH` 指过去。也可以对着已经起好的服务器手动跑：

```
PORT=18787 DB_FILE=/tmp/zairyu-e2e.db ADMIN_TOKEN=test-admin ADMIN_TOKENS=e2e:e2e-reviewer-token-0123456789 npm start &
BASE=http://localhost:18787 ADMIN_TOKEN=test-admin E2E_KEEP_GOING=1 node e2e/browser.js
```

这样跑时服务商的几步会失败：它们要用管理员直接入驻（只有 `createApp({ allowDirectProvider: true })` 才开）和不延迟的新咨询通知，这两项不读环境变量，所以服务商的检查只能用 `npm run e2e` 跑。

邮箱那几步的验证码和提醒邮件从 `GET /api/admin/outbox` 读，定时提醒用 `POST /api/admin/reminders/run` 触发，所以服务器要用默认的发件方式（不设 `MAIL_SENDER`）。不需要配置 `ANTHROPIC_API_KEY`：助手接口的返回在浏览器里换成固定内容，其余请求都打到真实的服务器上。每次用新的数据库文件。`E2E_KEEP_GOING=1` 时某一步失败后继续跑完并一并报告。

## 敏感号码过滤

`src/validate.js` 的 `findSensitive` / `assertNoSensitive`，用在四处：咨询摘要（接口和助手草稿）、助手对话（这一轮的消息，以及带回来的历史里的每一段文字：用户的话、助手的话、工具调用的参数、工具结果）、服务商回复、事件备注。命中就返回 422，内容不落库、不转给服务商或模型。

检查分三步：

1. 归一化：NFKC（全角数字、全角字母、全角空格和符号与半角同样处理），去掉零宽字符和软连字符。
2. 先遮掉明确不是号码的数字：日期（`2026-11-30`、`2026/11/30`、`2026.11.30`、`20261130`）、后面跟着“年”的年份、时刻（`10:30`）、带千位逗号的金额（`1,200,000`）、`+` 开头的国际电话（合计 8 至 15 位）、`0` 开头分三段写的日本电话（合计 10 或 11 位）、本系统的编号（UUID）。
3. 剩下的按下表判断。“分隔符”指空格、制表符、换行、`-`、`.`、`_`、`·`、`・`、`ー`、各种横线、逗号、顿号、斜线、冒号、竖线、波浪线。

拦下的内容：

| 类别 | 规则 | 例子 |
|---|---|---|
| 个人编号 | 正好 12 位连续数字（前后不再连着数字） | `123456789012`、`１２３４５６７８９０１２` |
| 个人编号 | 一串只隔着分隔符（组间 1 至 3 个）的数字组，不论怎么分组，合计正好 12 位 | `1234 5678 9012`、`123456-789012`、`123 456 789 012`、`12345 6789012`、`1234/5678/9012`、`1234,5678,9012`、分三行写的 `1234` `5678` `9012` |
| 个人编号 | 夹在更长一串数字里的 4-4-4 分组（前后隔着逗号等与别的数字相连，且不是 4-4-4-4 的一部分） | `住址 1-2-3, 1234 5678 9012` |
| 个人编号 | 关键词（个人编号、个人番号、個人番号、マイナンバー、my number）后 12 个字符内开始的一串数字，不论怎么分组、用哪种分隔符，合计正好 12 位。这一条不做下面“不拦”里的排除 | `个人编号：123 456 789 012`、`个人编号是 1234、5678、9012`、`my number: 1234/5678/9012` |
| 护照号 | 1 个字母加 8 位数字，或 2 个字母加 7 位数字，前后不连着别的字母数字 | `E12345678`、`EA1234567`、`tk1234567` |
| 护照号 | “护照”“passport”“旅券”“パスポート”后 8 个字符内，1 至 2 个字母、一个空格、7 至 8 位数字 | `passport E 12345678` |
| 护照号 | 关键词（护照号、护照号码、护照编号、旅券番号、パスポート番号、passport no / number / #）后 8 个字符内开始的一串数字，合计 6 至 9 位，且不是日期 | `护照号码是 12345678` |
| 银行卡、信用卡 | 16 至 19 位连续数字，或 4-4-4-4 分组（组间 1 至 3 个分隔符） | `4111111111111111`、`4111 1111 1111 1111`、`4111/1111/1111/1111` |
| 银行账号 | 关键词（账号、帐号、账户、卡号、银行卡号、信用卡号、储蓄卡号、借记卡号、口座、口座番号、カード番号、bank account、account no / number、IBAN）后 8 个字符内（中间不夹英文字母）开始的一串数字（这里的分隔符只算空格、点、横线），合计 7 位以上，且不是日期、后面不跟金额单位 | `账号 1234567`、`口座は 12345-12345678` |
| 银行账号 | “IBAN”后面的国别字母加数字的账号；“支店”或“店番”后面有“普通”“当座”再跟 7 位数字 | `IBAN GB29NWBK60161331926819`、`支店 123 普通 7654321` |

不拦的内容：

- 日期、时刻、两个日期连着写、日期加时刻（`2026/11/30 10:30`、`2026 1127 1530`、`202611271530`：12 位数字正好是年月日时分的不算个人编号）。
- 几个年份（每一组都是 19xx 或 20xx）：`需要 2023 2024 2025 三年的纳税证明`、`2023-2024-2025年度`、`2022 2023 2024 2025`。
- 电话：`090-1234-5678`、`09012345678`、`+81 90 1234 5678`、`+8190-1234-5678`、`+819012345678`。
- 金额：`1,200,000日元`、`12000000 日元`、`账户余额 1200000 日元`；分组写的 12 位或 16 位数字后面紧跟金额单位（日元、円、元、万等）的按价格处理：`套餐 2980/3980/4980 日元`、`月收 200000~250000日元`。
- 邮编、13 位的法人番号、在留卡号（`AB12345678CD`）。

已知的局限：这是按形状的拦截，不是识别。

- 拦不住的：没有关键词、又不是上面这些形状的号码（单独写的 7 位账号、中间夹着文字或字母的号码）；写成带千位逗号的金额样子（`123,456,789,012`）、前面加 `+`、后面加金额单位、或正好像年月日时分的 12 位数字，在没有关键词时也拦不住。
- 会误拦的，提示用户改写即可：
  - 和护照号同形的其他编号（1 个字母加 8 位数字、2 个字母加 7 位数字）：学号 `A12345678`、申请号 `E12345678`、`NH1234567` 这类。护照号没有校验位，按形状分不开；如果只在有“护照”字样时才拦，单独写的 `E12345678` 就漏了，所以选了宁可误拦。
  - 合计正好 12 位的其他数字：三个四位数连写且后面没有单位（`2980/3980/4980`）、不带单位的两个六位数（`200000-250000`）、不带 `+` 的 12 位国际电话、金额写成 `1234.5678.9012`。
  - “账号”后面紧跟的电话号码。

规则表在 `test/server-sensitive.test.js`（包括上面“会误拦”的例子），改规则时两处一起改；`test/assistant.test.js` 另有一条检查，保证服务器自己产生的工具结果（路线、方案、服务商名单）不会被这套规则拦下。
