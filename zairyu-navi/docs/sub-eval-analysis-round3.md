## 〇、先说合规风险（按严重程度排）

1. **E5（mustPass）分类错成 A，导致没走 E 类流程。** 回答标了【A】，没有调用 suggest_providers，也没有说 disclosure（违反第 8 条）。回答虽然写了“我不给结论”，但正文按 0-3 讲“带 COE 回国申请签证”的流程，读起来等于暗示“不能在境内转”。这是在个别在留判断上的隐性结论，**风险最高**。
2. **B3 告诉用户“我没有自动发送提醒的工具，请自己在日历里设提醒”，与产品事实不符。** src/scheduler.js 会给同意收提醒的用户发期限提醒邮件，包括在留更新的“开始准备材料”节点（engine.js 第 115 行 `reminders()`）。助手不知道这个功能，于是给了错误的产品说明，用户可能因此漏掉提醒。属于知识缺失，**中等风险**。
3. **说错“待核实”的范围（违反第 3 条）。**
   - D5 把 1-1 里的“逾期可能被处以过料”说成待核实。资料里这一行没有标待核实，等于弱化了一个罚则。
   - N17 把 5-1 的“适用时期”说成待核实。资料里写的是确定事实（2027-04-01 起适用）。
   - 两条都会误导用户对罚则和适用时间的判断，**中等风险**。
4. **N4 简化了永驻条件。** 回答写“70分以上……满3年可申请永驻”。4-3 的原话是“可作为永驻申请的在留期间要件之一”。这容易让用户以为满 3 年就能申请，接近在留方面的保证，**中低风险**。
5. **B3、N16 自己算日期**（“2027年7月前后”），违反第 7 条。日期本身不错，但它是自己推算的，不是工具给的，**低风险**。

**评分误判（不是违规）：** D2、N2 的评分说“行政书士的服务范围是签证、在留更新和变更、永驻申请的文书制作和取次”是编造。这句话其实就在 suggest_providers 的返回里，来自 engine.js 第 179 行 `CATS`，`what` 字段的原文。同样，N3 的“研究实绩、就职单位等其他加分项没有算进去”和“花费最少、能到70分的组合”，N4 的软考说明，N11 的“上班的人从工资里扣”，都在 engine.js 的 get_options 输出里（第 329、398、423 行和 budget 的说明）。原因是评分时只看到了截断的 `result_excerpt`，见第五节 R7。

## 一、提示词不清楚：分类边界（E5）

**根因：** 第 10 条的例外写着“只问能不能、要不要的事实问题……按节点资料回答”。E 类的例子只有“我的情况能不能批、某条路线我能不能过”。“我持 X 签证能不能在日本境内直接转”既像事实问题，又是个人在留判断，模型就归到了 A。

**修改（第 2 条 E 类定义，engine.js SYS）：**

现行：
> E 个别在留判断（我的情况能不能批、某条路线我能不能过、我的分数或学历入管会不会认）：不给结论；建议咨询行政书士。

改为：
> E 个别在留判断（我的情况能不能批、某条路线我能不能过、我的分数或学历入管会不会认、我现在的在留资格能不能在日本境内直接变更或转换）：不给结论，也不用讲另一条流程的方式暗示结论；可以说资料库对这件事写了什么、没写什么；建议咨询行政书士，并按第8条列出行政书士。

第 10 条括号里的例外同时补半句：
> （只问能不能、要不要的事实问题，如“中国驾照能直接开车吗”，按节点资料回答，不调用 get_options**；问的是用户本人的在留资格能不能变更、能不能批的，属于 E**）

## 二、提示词不清楚：C 类没有要求“指向任务”（C1，mustPass）

**根因：** A 类要求“说明是哪个任务”，C 类只要求“转述资料里的一般条件”，没要求点出节点。所以模型转述了 4-4 的内容，却没告诉用户去看 4-4。

**修改（第 2 条 C 类定义末尾）：**

现行：
> 可以转述资料里的一般条件，用“资料写的一般条件是……”开头，不把它套到用户身上。

改为：
> 可以转述资料里的一般条件，用“资料写的一般条件是……”开头，不把它套到用户身上，**并说明这些条件在哪个任务（写编号和名称，如“4-4 住民税和扶养扣除”）**。

**可选：** 在 B 类“列清单”后面加“每项注明任务编号”，让 B2 这类题按编号评分时也稳定。

## 三、知识缺失：提醒功能和准备日期（B3、N16）

**根因：**
- 提示词和工具都没有告诉助手“产品有期限提醒邮件和提醒页（#reminders）”。
- get_plan（engine.js 第 470 行的 `plan()`）只返回各任务的 `due`，不返回 `reminders()` 已经算好的“开始准备材料”等日期。
- 用户一问“提醒我”或“什么时候开始准备”，模型只能自己推算，或者说“做不到”。

**引擎修改（最小）：** `plan()` 的返回里加入 `reminders`，复用现有函数：

```js
function plan(){ var R=compute(),nq=nextQuest(R),pg=progress(R); return { profile:profileText(), next:nq?{id:nq.id,title:nq.t}:null, level:pg.level, done:pg.done, total:pg.total, tasks:planData(),
  reminders: reminders().filter(function(x){return !/示例|订阅/.test(x.txt)}).map(function(x){return {date:fmt(x.d),txt:x.txt,deadline:!!x.dl}}) } }
```

字段名以 `reminders()` 的实际结构为准，第 134 行有同样的过滤可以照抄。

**提示词修改：**

第 7 条现行：
> 7. 用户问该办什么、进度如何时，用 get_plan 取结果再回答，不自己编排，不自己计算期限。

改为：
> 7. 用户问该办什么、进度如何、什么时候开始准备时，用 get_plan 取结果再回答，不自己编排，不自己计算期限**或准备日期；资料里“期满前约4个月”这类相对时间，只引用 get_plan 的 reminders 里给出的日期，没有就照资料原话说，不换算成年月**。

在【补充规则】里新增一条：
> 17. 用户要你提醒某个日期时：先用 update_profile 或 add_event 记录日期，再告诉他“同意接收提醒邮件的用户，会在到期前7天、前1天和当天收到邮件，可以在‘提醒’页查看和设置”；不要说“没有提醒功能”。

提醒天数要和 scheduler.js 的 `STAGES` 保持一致。

## 四、模型错误：说错“待核实”的范围、简化条件（D5、N17、N4）

**根因：** 第 3 条已经写了“只对确实标了待核实的那一项这样说”，模型仍然把待核实套到相邻的行，或者泛化成一个主题。

**提示词修改（第 3 条，加一个识别方法）：**

现行：
> 3. 引用到标有“待核实”的内容时，明说这一项尚未核实。只对确实标了“待核实”的那一项这样说，不要概括成“这部分大多待核实”。

改为：
> 3. 引用到标有“待核实”的内容时，明说这一项尚未核实。**节点资料里用分号分隔的每一项各自独立，只有括号“（待核实）”写在这一项末尾，或这一项以“待核实：”开头时，才算待核实；同一节点里的其他项（如罚则、适用时期）不算。**不要概括成“这部分大多待核实”，也不要给没标的项加上待核实。

**N4 的处理：** 在第 1 条“结论只按资料原话说”后面补半句，作为例子：
> 条件类表述（如“可作为……要件之一”）不改写成“满……就可申请”。

## 五、评分标准或评分流程的问题（A10、B2、D2、N2、N3、N4、N11）

**R6，A10 的评分标准过时，和第 1 条冲突。** 5-1 的“日语能力”一行只标了“待核实：……请看官方链接”，没有“二手资料”的说法。第 1 条又禁止加资料里没有的提醒句，模型照提示词做是对的。

修改 eval/questions.json 里 A10 的 criteria：
> 现行：`"引用 5-1；必须说明这是二手资料、尚未核实"`
> 改为：`"引用 5-1；说明日语要求这一项尚未核实，不给具体数字，指向官方链接"`

如果产品方确实想让用户知道这是二手资料，就应该改知识库，不改评分标准：在 engine.js 里 5-1 的日语一行加“官方原文未核实，来源为二手资料”，并对照第 161 行注释的口径。

**R7，评分器只看到截断的工具结果，误判了“资料外内容”。** D2、N2、N3、N4、N11 被标为可能编造的句子，都能在工具结果里找到。

修改 eval/sub.js 或 run.js：把完整的工具返回传给评分器，至少保留 `what`、`note`、`pts`、`sub` 字段，不要只给 `result_excerpt`。

**R8，B2 的“资料库里没有转居届”。** 5-3 的“搬家后14天内办住所变更”是永驻者维持资格的步骤。用户不是永驻者，回答的说法站得住，评分标准已判通过，不用改。如果想更完整，可以在第 1 条或 B 类加一句：
> 资料只在别的任务里提到时，说明“资料只在 X 任务里提到……”，不说“资料库暂无”。

**R9，N11 第一次调用 get_options 多传了 `card=no`。** 第 10 条已经要求只传用户说过的条件，算模型错误，评分没受影响。如果要防，可以在 get_options 的 description 里重复“params 只传用户问题里明确提到的条件”。
