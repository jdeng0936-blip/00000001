## 建议的顺序

1. **先做 `owner-inputs.md` 的第 1–5 项**（公司信息、窗口邮箱、域名、邮件服务商、云服务商）。律师要看的条款里，这几项决定了怎么写（例如邮件服务商在国外，隐私政策就要多写一段，律师的 Q2 也跟着变）。金额、振込先、登记号（第 6–8 项）可以晚一点，但要在批准第一家服务商之前。
2. **同时开始 `field-checks.md`**。它不依赖别的，谁有空谁去；网上能做完的 11 条一两天就能做完，电话和门店的 7 条要跑腿。做完交给开发改 `data/nodes.json`。
3. **发 `gyoseishoshi.md`**。不依赖第 1 步，可以和第 2 步同时发。行政书士答完后，开发改资料、代码（届出的划分、积分的显示）和 `docs/compliance-review.md` 第三、四节。第 4 部分 Q25（转让账户的刑罚）和 `field-checks.md` 第 7 条是同一件事，哪边先有确定答案就用哪边。
4. **发 `lawyer.md`**（第 1 步的信息填进去以后）。律师答完后，开发改三份条款；律师的结论如果影响行政书士的部分（例如士业广告 Q7 和行政书士的 Q31），两边对一下。
5. **`owner-inputs.md` 第 9 项：配好 `ANTHROPIC_API_KEY`，用真实模型跑题集并逐条复核**。最好在行政书士回答第 6 部分（D、E、F 类边界）之后再做最后一轮，边界有变化时提示词要先改。
6. 全部回来后：开发更新 `docs/TODO.md`（第 3、5、7、8、9 条）和 `docs/compliance-review.md`，跑 `npm test`、`npm run e2e`，三份条款定稿时按 README“条款版本”的规则决定改不改版本号。

## 发出前

- `gyoseishoshi.md`、`lawyer.md` 开头的中文摘要是写给你的，发给对方时可以删掉。
- 两份日语资料都写明了“很多官方网站没能直接打开、部分内容来自搜索摘录”，这是事实，不要删。
- 这些资料里没有任何用户的个人信息，也没有密钥。`owner-inputs.md` 只给你自己看，里面的环境变量样例全是占位。
- 发现资料里的原文和 App 现在的不一致（代码在这之后又改过），以 App 为准，告诉开发更新这里。

## 写这批资料时发现的、要开发留意的不一致

这几处已经写进对应的资料里请对方确认，这里汇总，方便开发提前看：

1. `docs/compliance-review.md` 第三节说在线学位“确认前不显示加分数字”，但“高度人才积分规划”的方案卡片（`src/engine.js` 的 `RT`）会显示加分后的分数，只附“在线学位的实际审查口径请行政书士确认”（`gyoseishoshi.md` Q1）。
2. `eval/questions.json` 的 D5、N20 的判定要点写“可解释各栏含义”，系统提示 D 类写“不描述表格在哪里领、怎么填”，两边口径不一样（`gyoseishoshi.md` Q27、Q28）。
3. 使用条款第5条写非士业“可能向我们支付推广费”，实际所有服务商只付固定展示费（`lawyer.md` Q6）。
4. 节点 5-3 的概要已经去掉施行日，但同一节点“施行日和‘故意’的标准”一行（待核实、隐去数字）的原文里仍写着“从2027年4月1日起施行”（`gyoseishoshi.md` Q13）。
5. 名单为空时助手照说“以下服务商……”，读起来不通（`docs/sub-eval-analysis-round4.md` 根因 4，`lawyer.md` Q5）。
6. 已定“登记适格请求书之前不开始收费”，但代码不拦：不填登记号也照常开账单（`owner-inputs.md` 第 8 项）。
